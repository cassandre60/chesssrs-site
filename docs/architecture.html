Architecture

System Architecture & Foundation

The technical design of ChessSRS: Lichess Mobile GPL-3.0 base, pure domain boundaries, Riverpod 3.x, and local persistence.

Source in app repo: ARCHITECTURE.md
App version: v1.4.0
Licence: GPL-3.0

1. The Foundation Reset

ChessSRS is built on a direct fork of Lichess Mobile (lichess-org/mobile), licensed under GNU General Public License v3.0 (GPL-3.0).

The previous standalone Flutter prototype was permanently archived at git tag legacy/pre-reset. It serves as reference material only: the product contracts and domain behavior are implemented cleanly within the Lichess Mobile architectural patterns.

Lichess Mobile provides a battle-tested foundation: high-performance chessground board rendering with 60fps animations, rock-solid move legality validation via dartchess, native audio synthesis, and proven Riverpod state-management patterns. On top of this foundation, ChessSRS replaces online multiplayer with a local-first spaced repetition repertoire engine.

2. Layer Boundaries & Component Responsibilities

The codebase is structured into four strict architectural tiers:

Architectural Layer Dependency FlowASCII Diagram
┌────────────────────────────────────────────────────────────┐
│ Presentation — Lichess Mobile shell (Flutter + Riverpod)    │
│   Review screen · Scope drawer · Library sheet · Settings  │
└──────────────────────────┬─────────────────────────────────┘
                           │ talks only to application providers
┌──────────────────────────▼─────────────────────────────────┐
│ Application — Riverpod providers/services orchestrating    │
│   use-cases (import study, start review, submit move)      │
└──────────────────────────┬─────────────────────────────────┘
                           │ repository interfaces only
┌──────────────────────────▼─────────────────────────────────┐
│ DOMAIN (pure Dart, zero Flutter/chessground imports)        │
│   Study · Chapter · RepertoireDecision · ReviewState       │
│   ReviewSession engine · FSRS Scheduler contract           │
└──────────────────────────┬─────────────────────────────────┘
                           │ adapters only
┌──────────────────────────▼─────────────────────────────────┐
│ Infrastructure — Lichess-derived:                          │
│   dartchess (rules, FEN, SAN, PGN) · chessground widgets   │
│   sqflite local DB · settings/preferences · file import   │
│   (no network on any critical path)                        │
└────────────────────────────────────────────────────────────┘

Detailed Responsibilities

  • Domain Layer (Pure Dart): Resides in lib/src/domain/. Encapsulates all chess repertoire tree logic, decision scheduling, memory models, and state transitions. Absolutely zero imports of Flutter UI widgets, Riverpod, or SQLite. Testable without starting a Flutter widget engine.
  • Application Layer: Riverpod controllers and services (such as ReviewController, StudyController). Orchestrates user actions, translates domain states into view-ready models, and coordinates local storage writes.
  • Presentation Layer: Flutter widgets implementing the custom "Diagram" aesthetic. Clean typographic hierarchy, zero distraction, responsive layouts adapting seamlessly from mobile phones to tablets and desktops.
  • Infrastructure Layer: Platform adapters, SQLite database drivers via sqflite, file system I/O, and the Stockfish UCI engine integration.

3. Non-Negotiable Boundary Invariants

INV-PURE-DOMAIN

Our domain code contains pure Dart entities and business algorithms. Zero imports of package:flutter/..., chessground, or sqflite. Mechanically enforced by automated static analysis in gate G03 (scripts/gates/banned_apis_check.py).

INV-SINGLE-CHESS-REP

dartchess is the sole chess rules and position engine. Do not introduce competing chess libraries or re-implement move generation. The domain consumes dartchess core types (Position, Move, San) through thin adapters; presentation consumes chessground.

INV-LOCAL-FIRST

The entire critical user loop—making a move, validating legality, checking repertoire expectations, updating FSRS memory states, and updating the board—executes in memory and local SQLite. Network access is completely absent from this path.

4. Subsystem Cuts & Retentions

To transform Lichess Mobile into a quiet, focused training sanctuary, non-repertoire systems were cleanly removed per CUT_PROPOSALS.md:

Subsystem Status Rationale
Online multiplayer / matchmaking / lobby Removed Offline repertoire recall does not require real-time games.
TV, streaming, chat & social feed Removed Eliminates distraction and social anxiety; reinforces calm training.
Leaderboards, badges & XP gamification Removed Promotes intrinsic recall habit over artificial streak inflation.
Lichess Puzzles & Puzzle Storm Removed App focuses exclusively on user-curated opening repertoires.
Chessground board renderer & animations Retained & Adapted World-class touch responsiveness, piece gestures, and board visuals.
dartchess rules & move validator Retained High-performance, memory-safe chess representation.
Audio synthesizer & piece sound effects Retained Provides immediate tactile feedback on move recall.
Stockfish engine integration Retained (Local Analysis) Enables on-device deep exploration without network dependency.

5. Local Persistence (SQLite / Drift)

Repertoire content and review histories are persisted in a local SQLite database (managed via sqflite and drift schema migrations):

  • Incremental writes (INV-002): Answering a move writes the updated ReviewState and records a ReviewEvent row only. The repertoire move tree is never serialized or rewritten on every move.
  • Crash consistency (INV-001): A graded review answer is committed within an atomic database transaction. Closing or killing the process immediately after a move preserves the exact review state.
  • Deduplication on import (INV-003): PGN trees are hashed canonically. Re-importing the same study updates metadata without duplicating decisions or corrupting existing intervals.
