Data Architecture

Domain Model & Schemas

The domain vocabulary, entity hierarchy, position identity keys, and SQLite database schema.

Source in app repo: docs/domain-model.md
App version: v1.4.0
Licence: GPL-3.0

1. Core Domain Entities

The domain model resides strictly in lib/src/domain/, modeled as immutable data classes:

  • Study: The top-level repertoire collection imported from a single source (PGN file or Lichess study URL). Contains metadata and one or more Chapters.
  • Chapter: A named logical unit from the PGN, corresponding to a single game header or study chapter. Contains root move node and orientation.
  • PositionNode / Variation: A node in the branching chess tree. Tracks FEN state, parent pointer, incoming move, and child moves (variations).
  • RepertoireDecision: The atomic scheduled unit of spaced repetition. Links a specific position with the expected repertoire move.
  • ReviewState: Spaced repetition tracking data (current stability, difficulty, repetitions, lapse count, next due timestamp).
  • ReviewEvent: Immutable log record of an active recall attempt (rating, timestamp, review duration, stability change).

2. The RepertoireDecision Unit

In an opening repertoire, you do not review opponent moves—you only review your own planned replies!

RepertoireDecision StructureConcept
RepertoireDecision {
  String id;                 // Unique decision identifier
  String studyId;            // Parent study
  String chapterId;          // Parent chapter
  String fen;                // Board position (FEN4)
  Move expectedMove;         // The user-prepared move (UCI)
  String canonicalStateId;   // Pointer to shared ReviewState (for transpositions)
}

Opponent choices represent branch forks. Each of your planned responses constitutes a RepertoireDecision.

3. Review State Lifecycle

A position transitions across distinct memory stages:

  1. Fresh / Unseen: Position has been imported but never reviewed. Positioned in the "Fresh" pool, introduced gradually according to the "New positions per day" limit.
  2. Learning: Undergoing initial acquisition. Intervals are measured in hours or single days until basic retention is proven.
  3. Retained / Active Review: Governed by continuous FSRS power-law scheduling. Intervals expand geometrically as stability increases.
  4. Lapsed: Move was missed during review. Moves into intra-session buffer, receives stability reduction, and resets to short intervals until regained.

4. SQLite Database Schema

Persistence uses SQLite tables with indexed keys for fast query execution on mobile devices:

Core Database TablesSQL DDL
-- Studies table
CREATE TABLE studies (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  pgn_hash TEXT NOT NULL,
  source_type TEXT NOT NULL,
  created_at INTEGER NOT NULL
);

-- Repertoire chapters
CREATE TABLE chapters (
  id TEXT PRIMARY KEY,
  study_id TEXT NOT NULL REFERENCES studies(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  side TEXT NOT NULL, -- 'white' or 'black'
  sort_order INTEGER NOT NULL
);

-- Decisions & review states
CREATE TABLE review_states (
  canonical_id TEXT PRIMARY KEY, -- sha1(fen4 + uci)
  stability REAL NOT NULL,
  difficulty REAL NOT NULL,
  repetitions INTEGER NOT NULL,
  lapses INTEGER NOT NULL,
  last_reviewed_at INTEGER,
  next_due_at INTEGER NOT NULL
);

CREATE INDEX idx_review_states_due ON review_states(next_due_at);
